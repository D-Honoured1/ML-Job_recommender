1. PROJECT OVERVIEW
================================================================================

HJR-System is a full-stack hybrid job recommender system built as a dissertation
project. It combines Content-Based Filtering (CBF) and Collaborative Filtering
(CF) into a single weighted hybrid model that adapts its strategy per user
based on how much interaction history they have accumulated.

Key design goals:
  - Cold-start safety: new users with no history get pure CBF (profile-driven)
  - Progressive personalisation: as interactions grow the CF signal increases
  - Real-user support: registered accounts use their DB profile and interactions
  - CSV fallback: 500 synthetic users (U001-U500) allow testing without login

The system is composed of:
  - A Django REST API (backend) that hosts the recommendation engine and auth
  - A React single-page app (frontend) that renders cards and captures clicks
  - A PostgreSQL database for user accounts, profiles, and job interactions
  - Three CSV files (data/) that seed the job catalogue and synthetic users

                    job_title+company pairs removed, first occurrence kept)

  Job IDs : J0001 – J2500 (non-contiguous after deduplication)
  Skills  : semicolon-separated (e.g. "Python;Django;REST APIs")

---- users.csv --------------------------------------------------------------

  Rows    : 500
  Columns : user_id, current_title, education, skills, experience_years
  User IDs: U001 – U500
  Skills  : semicolon-separated

---- interactions.csv -------------------------------------------------------

  Rows    : 4,869  (remapped and deduplicated after job deduplication;
                    original 5,129 rows reduced by collapsing references to
                    removed duplicate job IDs back to their canonical job ID)
  Columns : user_id, job_id, interaction
  Values  : interaction = 1 (positive: applied / interested)
                        = 0 (negative: skipped)

  Most active user  : U162 — 13 positive interactions
  Mid-range example : U083 — 7 positive interactions

Deduplication rationale:
  The original 2,500-job dataset contained 497 pairs where job_title and
  company were identical. These caused the CF engine to return 5 copies of
  the same job title/company in top-N results. Deduplication resolved this
  while preserving all distinct job listings.

5. SYSTEM ARCHITECTURE
================================================================================

Django startup sequence:
  RecommenderConfig.ready()
      ├── Read jobs.csv, users.csv, interactions.csv into pandas DataFrames
      ├── Cast all ID columns to str
      └── build_engine(job_df, user_df, interaction_df)
              └── HybridRecommender.__init__()
                      ├── ContentBasedFilter.fit(job_df)   — builds TF-IDF matrix
                      └── CollaborativeFilter.fit(interaction_df)  — builds pivot table

The engine is held as a module-level singleton (_recommender). All requests
share the same fitted model; no re-fitting on each request.

Request flow (unauthenticated / CSV user):
  GET /api/recommendations/?user_id=U001&n=5
      └── RecommendationsView.get()
              ├── Validate params
              ├── get_recommender().recommend(user_id="U001", n=5, db_user=None)
              │       ├── _dynamic_weights("U001") → (α, β)
              │       ├── CBF: ContentBasedFilter.score(user_row) → {job_id: score}
              │       ├── CF:  CollaborativeFilter.score("U001")  → {job_id: score}
              │       ├── hybrid[j] = α × cbf[j] + β × cf[j]  for each job
              │       └── return sorted top-n as list[dict]
              └── Return JSON with user_id, weights, count, recommendations

Request flow (authenticated / DB user):
  GET /api/recommendations/?n=5
  Authorization: Bearer <access_token>
      └── RecommendationsView.get()
              ├── JWT decoded → db_user = request.user
              ├── user_id = "db_{db_user.pk}"
              ├── get_recommender().recommend(user_id, n, db_user=db_user)
              │       ├── _dynamic_weights uses JobInteraction.objects.count()
              │       ├── CBF: _profile_to_series(db_user) → Series from UserProfile
              │       └── CF:  _cf_scores_for_db_user() → rebuild matrix with DB rows
              └── Return JSON

Interaction tracking flow:
  POST /api/jobs/interact/
  Authorization: Bearer <access_token>
  Body: { "job_id": "J0042", "interaction_type": "viewed" }
      └── JobInteractView.post()
              └── JobInteraction.objects.create(user, job_id, interaction_type)

6. RECOMMENDATION ENGINE
================================================================================

File: backend/recommender/engine.py

--------------------------------------------------------------------------------
6a. Content-Based Filtering (CBF)
    Class: ContentBasedFilter
--------------------------------------------------------------------------------

Represents every job and each user as a TF-IDF vector, then scores jobs by
cosine similarity to the user's profile vector.

Job document (built from CSV or job_df row):
  "{job_title} {required_skills (;→space)} {description}"  (lowercased)

User document (built from user_df row or UserProfile):
  "{current_title} {education} {skills (;→space)}"  (lowercased)

TF-IDF configuration:
  analyzer      = "word"
  ngram_range   = (1, 2)   — unigrams and bigrams
  min_df        = 1
  stop_words    = "english"
  sublinear_tf  = True

Score range: [0.0, 1.0]  (cosine similarity)

Methods:
  fit(job_df)          → builds self._job_matrix (sparse TF-IDF), self._job_ids
  score(user_row)      → returns dict {job_id: float}

--------------------------------------------------------------------------------
6b. Collaborative Filtering (CF)
    Class: CollaborativeFilter
--------------------------------------------------------------------------------

User-based CF using Pearson correlation on a User-Item interaction matrix.

Interaction matrix:
  pivot_table(index="user_id", columns="job_id", values="interaction", fill_value=0)

Neighbour selection:
  - Pearson correlation over union of non-zero items for each user pair
  - Minimum 2 shared items required (otherwise skipped)
  - Users with zero variance in their interaction vector are skipped
  - Top-K = 5 neighbours selected

Score formula for job j and user u:
  S_CF(u, j) = Σ[ sim(u,v) × r(v,j) ] / Σ|sim(u,v)|   (over top-K neighbours)
  Clamped to [0.0, 1.0]

For authenticated DB users: _cf_scores_for_db_user() merges CSV interactions
with the user's live DB JobInteraction rows into a temporary matrix, scored
without modifying the global CF instance.

Methods:
  fit(interaction_df)  → builds self._matrix (pivot table)
  score(user_id)       → returns dict {job_id: float}

--------------------------------------------------------------------------------
6c. Hybrid Scoring & Dynamic Weights
    Class: HybridRecommender
--------------------------------------------------------------------------------

Final score:
  S_Hybrid(u, j) = α × S_CBF(u, j) + β × S_CF(u, j)

Dynamic weight formula (_dynamic_weights):

  count = number of positive interactions for the user

  if count < MIN_INTERACTIONS (3):
      α = 1.0,  β = 0.0          ← pure CBF (cold start)
  else:
      t = min(1.0,  log1p(count - 3) / log1p(10))
      α = 1.0 - t × (1.0 - MIN_CBF_ALPHA)    floor  = 0.30
      β = t × MAX_CF_BETA                     ceiling = 0.70

Constants:
  MIN_INTERACTIONS = 3
  MAX_CF_BETA      = 0.7
  MIN_CBF_ALPHA    = 0.3

Weight examples by interaction count:
  count  0–2  →  α=1.0000,  β=0.0000  (pure CBF)
  count  3    →  α=1.0000,  β=0.0000  (threshold, still pure CBF)
  count  4    →  α=0.7977,  β=0.2023
  count  7    →  α=0.5302,  β=0.4698
  count  13   →  α=0.3000,  β=0.7000  (cap reached)
  count  14+  →  α=0.3000,  β=0.7000  (capped)

Rationale: log scaling means the shift from CBF to CF happens quickly in the
early interactions (3→7) and then slows, reflecting diminishing marginal
information per new interaction at higher counts.

Singleton pattern:
  build_engine(job_df, user_df, interaction_df)  — called once at startup
  get_recommender()                              — returns the singleton

7. BACKEND — DJANGO REST API
================================================================================

Base URL (development): http://localhost:8000/api/

--------------------------------------------------------------------------------
7a. URL Routes
--------------------------------------------------------------------------------

  /api/auth/register/           POST   Create account (+ optional profile fields)
  /api/auth/login/              POST   Obtain JWT access + refresh tokens
  /api/auth/logout/             POST   Blacklist refresh token
  /api/auth/token/refresh/      POST   Exchange refresh token for new access token
  /api/auth/profile/            GET    Retrieve authenticated user's profile
  /api/auth/profile/            PUT    Update authenticated user's profile
  /api/auth/profile/resume/     POST   Upload PDF resume; extract + save skills
  /api/recommendations/         GET    Get top-N job recommendations
  /api/jobs/interact/           POST   Log a job interaction (viewed / applied)

--------------------------------------------------------------------------------
7b. Authentication (JWT)
--------------------------------------------------------------------------------

Library: djangorestframework-simplejwt

  Access token lifetime  : 24 hours
  Refresh token lifetime : 7 days
  Rotation               : enabled (new refresh token on each refresh)
  Blacklist              : enabled (old refresh tokens are invalidated)
  Auth header format     : Authorization: Bearer <access_token>

Tokens are stored in the browser's localStorage:
  localStorage.getItem("access_token")
  localStorage.getItem("refresh_token")

The Axios instance in api.js automatically:
  - Injects the Bearer token on every outgoing request
  - Intercepts 401 responses and attempts a silent token refresh
  - Redirects to /login if the refresh also fails

--------------------------------------------------------------------------------
7c. User Profile & Resume Upload
--------------------------------------------------------------------------------

Registration accepts:
  username (required), email, password (required),
  current_title, education, skills (comma-separated), experience_years

Resume upload (POST /api/auth/profile/resume/):
  - Accepts a PDF file (multipart/form-data, field name "resume")
  - Extracts text using pypdfium2
  - Parses skill tokens using NLTK
  - Saves extracted skills (semicolon-separated) to UserProfile.skills
  - Returns { "extracted_skills": [...] }

During registration, resume upload mode:
  1. Creates the account with username + password
  2. Logs the user in (stores tokens)
  3. Uploads resume and extracts skills
  4. Navigates directly to the recommendations page

--------------------------------------------------------------------------------
7d. Job Interactions
--------------------------------------------------------------------------------

Endpoint: POST /api/jobs/interact/
Requires:  Authorization: Bearer <token>
Body:      { "job_id": "J0042", "interaction_type": "viewed" }

Interaction types accepted: "viewed", "applied"

Every click on a job card or the Apply button in the frontend fires this
endpoint. The interaction is stored in the JobInteraction table and is used
by the CF engine to re-weight recommendations for that user.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
8c. API Client (api.js)
--------------------------------------------------------------------------------

Axios instance:
  baseURL: "/api"  (proxied to http://localhost:8000 by CRA in development)

Request interceptor:
  Reads access_token from localStorage and injects:
  Authorization: Bearer <token>

Response interceptor:
  On 401: calls POST /api/auth/token/refresh/ with stored refresh_token
           On success: retries original request with new token
           On failure: clears tokens and redirects to /login

--------------------------------------------------------------------------------
8d. Interaction Tracking (RecommendationsPage.jsx)
--------------------------------------------------------------------------------

trackInteraction(jobId):
  - No-op if user is not logged in (isLoggedIn check)
  - Reads access_token from localStorage
  - POST /api/jobs/interact/
      body:    { job_id: jobId, interaction_type: "viewed" }
      header:  Authorization: Bearer <token>
  - try/catch swallows all errors — never interrupts the UI

handleApply(jobId):
  - Calls trackInteraction(jobId)
  - Opens /jobs/{jobId}/apply in a new browser tab

12. KNOWN LIMITATIONS & FUTURE WORK
================================================================================

Current limitations:
  1. CF scores are lower in absolute magnitude than CBF scores.
     When blended, the hybrid score is numerically smaller than a pure-CBF score
     even if CF carries useful signal. Future work: normalise CBF and CF score
     distributions before blending (e.g., min-max or z-score normalisation).

  2. CF requires at least 3 positive interactions before activating and depends
     on finding neighbours with shared interaction history. Users whose profile
     is very niche may find no useful neighbours, causing CF to contribute zero.

  3. The engine is loaded once at startup and held in memory. New CSV rows
     (e.g., a refreshed jobs.csv) require a server restart to take effect.
     DB user interactions are merged dynamically; CSV data is static.

  4. Jobs are matched against user skills via TF-IDF which treats skill tokens
     as bag-of-words. Synonyms ("JS" vs "JavaScript") and compound skills
     ("machine learning" vs "ML") may not match unless both forms appear in the
     TF-IDF vocabulary. Future work: skill normalisation / embedding-based CBF.

  5. No evaluation suite for the 500-user, 2,003-job dataset exists yet.
     The metrics in the old documentation.md apply to the original 20-user
     dataset and are no longer representative.

Future work:

  - Skill normalisation layer before TF-IDF vectorisation
  - Score normalisation before hybrid blending
  - Implicit feedback (dwell time, scroll depth) in addition to clicks
  - Pagination for the recommendations grid
  - Admin view showing interaction logs per user
